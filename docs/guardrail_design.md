# 护栏设计：三层各自能挡什么，以及**挡不住什么**

> 这份文档的规矩：**「挡不住什么」比「挡什么」重要。**
> 一个只说能挡什么的护栏文档，读的人会以为没写的就是被挡住的。
> 所以每一层都必须写清楚它的失效边界，且边界要**有实测支撑**，不能是"我觉得"。
>
> 失效边界不是免责声明，是**设计输入**：S3 实测出「Layer 0 拦下导航会把标签留成
> 空白页」之后，Layer 1 的定位才从"第二道网"变成"**必须**在动作执行前拦"。
> 边界决定了架构，不是反过来。

## 实现状态（先看这个，避免把设计当成现状读）

| 层 | 状态 | 在哪 |
|---|---|---|
| Layer 0 网络层 | **已实测**（S3 / S7） | 库的 `SecurityWatchdog`，由 `compiler.py` 装配 `browser_kwargs` |
| Layer 1 动作层 — 策略 | **已实现并测**（19 条用例） | `guardrails/{rules,policy}.py` |
| Layer 1 动作层 — 拦截器 | ⬜ **未落盘**，随 Phase 4 的 mock 站点一起做 | `guardrails/interceptor.py`（计划中） |
| Layer 2 结果层 | ⬜ **未落盘**，Phase 3 | `store/` + 输出校验（计划中） |

**所以现在这份文档描述的是：一层已在真实浏览器上验证过、一层策略已定但还没接到真实
run 上、一层只有设计。** 把这三者写成一个样子才是真正危险的。

---

## 总览

```
Layer 0  网络层   SecurityWatchdog（库自带，白名单装配）
         挡：导航到站外、重定向到站外、新 tab 到站外
         挡不住：站内的任何操作；页面内 fetch()/XHR 到站外（不是导航事件）

Layer 1  动作层   GuardrailInterceptor（本项目核心工作）
         挡：站内的危险动作（删除/下架/支付/发布/编辑），且在动作【执行前】
         挡不住：LLM 用两个"无害"动作组合出危险效果（先"全选"再"批量操作"）

Layer 2  结果层   输出校验 + 入库前过滤
         挡：schema 漂移、幻觉字段、把"删除成功"提示当商品数据
         挡不住：真实但错误的数据 → 人工抽检 + suspicious 标记
```

---

## Layer 0：网络层

**怎么装配**：`dsl/compiler.py` 把 DSL 的 `allowed_domains` / `prohibited_domains`
放进 `browser_kwargs`，由 `BrowserSession(...)` 交给库的 `SecurityWatchdog`。
本项目**不重新实现**它，也不依赖它做动作级拦截。

### 实测：拦得住，但代价比计划里写的大

S3 的逐字输出：

```
每一步的 URL:
  step 0: about:blank
  step 1: http://127.0.0.1:18838/
  step 2: about:blank
  step 3: about:blank
错误:
   Navigation failed: Navigation to http://localhost:18838/page2 blocked by security policy

【关键发现】被拦之后的页面: 'about:blank'
SPIKE_S3_OK
```

计划里原本的判据只到「错误信息里能读出是安全策略拦的，run 不崩」——那两条都成立。
但**被拦的导航把标签留在了 `about:blank`**：step 1 还在站点页，step 2 就空了。

这条改变了 Layer 0 的定位：

> **Layer 0 是「最后一道网」，不是「拦下来之后还能继续干活」的机制。**
> 拦下一次导航 = 顺手弄丢当前页面 = 后面所有提取采到的都是空。

于是 Layer 1 必须在**动作执行前**拦 —— 那样根本不产生导航，页面状态不会被破坏。
这是"实测边界反过来决定架构"的一个具体例子。

### 挡不住什么

- **站内的任何操作**。白名单管的是"去哪"，不管"到了之后干什么"。这是 Layer 1 的全部存在理由。
- **页面内的 `fetch()` / XHR 到站外**。那不是导航事件，`SecurityWatchdog` 不看它。
  缓解：`policy.check_navigation()` 提供了**导航前置校验**（可在动手之前判定、测试、审计），
  但它是"导航前"的检查，同样管不了页面内自发请求。
  **这条没有完整解法，只能靠"任务本身只读 + 白名单尽量窄"来压住影响面。**
- **已经被导航过去的页面**。一旦过去，页面上的脚本已经执行了 ——
  所以 `check_navigation` 里"配了白名单但没命中 → 一律 block，不回落到
  `default_decision`"是刻意的：白名单的语义是"只允许这些"，回落会让它变成"建议清单"。

### 什么情况下本节的结论会失效

库改成"拦下导航时不改变当前标签的 URL"。届时应重跑 S3，本文件同步改。

## Layer 1：动作层（本项目核心工作）

### 规则匹配语义：四个维度 **AND**

| 维度 | 语义 |
|---|---|
| `match_action` | 精确匹配动作名 |
| `match_url` | **SecurityWatchdog 语义**的 fnmatch（两套匹配器不一致，见下） |
| `match_element_text` | 正则，不区分大小写 |
| `match_param_regex` | 对 `json.dumps(params, sort_keys=True)` 做正则 |

四者**全空 = 匹配一切**；任一维度不满足即整条不命中。

两个刻意的设计：

- **`match_url` 用 SecurityWatchdog 的语义，不用 `browser_use/utils.py` 那套。**
  库里有**两套互不兼容**的域名匹配器（`security_watchdog.py:252-296` 自带 fnmatch、
  要求 scheme ∈ {http,https}；而 `utils.py:563` 默认 scheme 是 https）。
  白名单以实际执行拦截的那套为准，否则会出现"策略说允许、执行时被拦"。
- **拿不到元素文本时【不命中】，而不是当空串。**
  当空串的话，`match_element_text: ""` 这类写错的规则会匹配一切 ——
  一个写错的规则从"不生效"变成"拦死所有操作"，方向完全反了。

### 决策聚合：**最严优先**（block > confirm > allow）

`Decision` 的严格程度由**显式 `severity` 字典**定义，不靠枚举定义顺序或字典序 ——
否则"往中间插一个新等级"就会静默改变所有比较结果。

聚合与 YAML 顺序**无关**。理由不是洁癖：

> YAML 是有顺序的。若采用"先匹配先赢"，那么**把一条 `allow` 规则写在 `block` 规则前面
> 就是一个静默的安全漏洞** —— 功能测试全过，review 的人从 YAML 上也看不出来，
> 因为那两条规则各自都对。最严优先让规则集的语义与顺序解耦：
> review 时只需看集合本身，不必同时判断顺序。

平局时按 `rule_id` 升序，**不按 YAML 顺序**。否则"两条 block 规则调换位置"会让报告里的
`rule_id` 变来变去，追溯时看着像行为变了，实际只是顺序变了。

### `default_decision` 默认是 `confirm`，不是 `allow`

**LLM 的失败模式恰恰是"做了你没预料到的那个动作"。**
默认放行等于护栏只在写了规则的地方生效 —— 而规则的盲区正是它最需要生效的地方。

### ⚠️ 最危险的一条：快照会被原地清空（S2-4 实测）

这是 S2 自己踩出来的，也是整个探路里最危险的一条：

```
── 判据 4：kill 前 selector_map=10，kill 后=0 ──
   dom_state 是同一个对象: True；dict 是同一个对象: True
   它与会话内部缓存 _cached_selector_map 是同一个 dict: True
── 判据 4b：keep_alive=False，run() 返回时 selector_map=0 ──
```

- `update_cached_selector_map()` **直接赋值、没有拷贝**（`session.py:2494`）→ 快照里的
  `selector_map` 和会话内部缓存**是同一个 dict 对象**；
- `reset()` 对它调 `.clear()`（`session.py:664`）—— **原地清空**；
- 而 `run()` 在 `keep_alive` 为假时**自己就会 reset**（事实 15）。

→ **默认配置下，`run()` 一返回，所有快照都已经是空的。**

**为什么它对护栏尤其致命**：失败形态是**静默的**。
一个存下 `browser_state`、想在最后统一处理的实现会拿到空 `selector_map`
→ **没有任何规则命中** → 而"没有任何规则命中"是一个**合法结果**（它就是
`default_decision` 那条分支）→ 不报错、不告警、测试全绿。

> **护栏看起来在跑，实际一步都没判。** 这比护栏崩溃危险得多 ——
> 崩溃会有人修，静默失效不会。

**已定死写法**：拦截器/记录器必须在拿到 `browser_state` 的那**一刻**把要用的东西取走，
**不能存下对象晚点再读**。（这条与计划里原本的写法冲突，计划原打算在 `Recorder` 里
收集状态最后统一处理，已按实测改掉。）

### 挡不住什么

- **两个"无害"动作组合出的危险效果**：先"全选"（allow）再"批量操作"（allow），
  合起来是批量删除。规则是**逐动作**判定的，看不到动作序列的语义。
  缓解：`max_consecutive_blocks` 硬停 + Layer 2 的结果校验 + 危险端点在 e2e 里
  用"真实 HTTP 层有没有被调用"来断言（见下）。
- **页面内容对 LLM 的诱导**（prompt injection）。页面文本会进 LLM 的上下文，
  页面里写一句"忽略之前的指示"是可能的。
  **但这一层的护栏天然不受它影响** —— 判定依据是「动作名 + 元素文本 + URL + 参数」，
  **不问 LLM 为什么这么决定**。所以注入没法让它点"批量删除"。
  真正被这层挡不住的是：把数据**填到某个站内允许的地方**（白名单限制了能去哪）。
- **LLM 选了一个合法但错误的目标**：比如在错误的商品行上点"编辑"。
  这是决策质量问题，不是护栏问题；靠 Layer 2 + 人工抽检。

## Layer 2：结果层

挡：schema 漂移、幻觉字段、把"删除成功"的提示当成商品数据。
挡不住：**真实但错误的数据**（把"近30天销量"填进"库存"列）→ 人工抽检 + `suspicious` 标记。

两条已定的取舍（Phase 3 落地）：

- **解析失败 = 整个 run 失败，不做 LLM 修复。**
  修复需要第二次 LLM 调用，那"修复后的值由谁负责"就答不上来：库里会存一个
  **经过 LLM 二次加工**的数，而它和页面上真实的值是什么关系，没人知道。
  对一个**电商卖家后台**的数据，这比"没采到"严重得多 —— 卖家可能拿这个数去补货。
- **`suspicious` 只标记、不删除。** 删掉就再也看不到"LLM 出错的方式"，而那正是最该看的。

## 明确不做

**不写任何反检测 / 拟人化代码**（延迟随机化、指纹伪装、验证码绕过）。
这不是能力问题，是合规判断：把 RPA 伪装得更像真人，从合规角度反而更危险，
且当年深圳某科技公司案的争议焦点正是这类行为。

---

## 怎么验证这层护栏真的在工作

**不要断言日志里有 block 记录** —— 那只证明代码走到了那一步。
mock 后台的 `/goods/delete/{id}` 在被调用时置一个模块级标志，
e2e 断言**这个标志为 False**：证明护栏在**真实 HTTP 层面**挡住了写入。

对照实验（本项目的通用手法）：先把标志**人为置 True** 跑一次，
确认断言会红；再正常跑，确认它是绿的。没有前一半，后一半可能是空转。

## 什么情况下要改这份文档

`spikes.md` 里每条判据都写了"什么情况下不成立"。汇总到这里：

| 结论 | 失效条件 |
|---|---|
| Layer 0 拦下导航会留空白页（S3） | 库改成拦下时不改变当前标签 URL |
| 快照会被 reset 原地清空（S2-4） | 库改成赋值前 `dict(...)` 拷贝，或 `reset()` 改成重新赋值 |
| 元素文本可稳定取得（S2-1/2/3） | `get_meaningful_text_for_llm()` 的优先级或序列化形态变了 |
| 白名单能匹配带端口的 IP 主机名（S7） | 库改域名匹配器 |

前两条尤其重要：它们各自都有 `tests/test_browser_contract.py` 里的守卫断言，
**库升级时守卫会先红**，红了就来改这里 —— 而不是让这份文档悄悄过期。
